
GAIN NIAGA KOIN - GO PUBLIC READINESS MASTER BLUEPRINT

TUJUAN DOKUMEN

Dokumen ini adalah blueprint perbaikan menyeluruh berdasarkan hasil audit source code yang telah diperiksa.
Fokus utama bukan sekadar memperbaiki bug, tetapi memastikan aplikasi layak digunakan publik, aman,
mudah dipelihara, mudah dikembangkan, dan siap bertumbuh tanpa menciptakan technical debt besar.

CATATAN PENTING

Semua poin di bawah dibagi menjadi:

- Fakta yang ditemukan dari source code.
- Risiko yang muncul.
- Target kondisi production.
- Langkah implementasi detail.

FASE 1 - CRITICAL BLOCKER (WAJIB SEBELUM GO PUBLIC)
=====================================================================

1. FIRESTORE SECURITY RULES HARDENING

Fakta:
- Aplikasi menggunakan Firestore sebagai database utama.
- Firestore Rules menjadi lapisan keamanan paling kritis.
- Belum dapat diverifikasi bahwa seluruh collection telah menggunakan ownership validation yang ketat.

Risiko:
- User membaca data user lain.
- User mengubah saldo user lain.
- User memanipulasi transaksi.
- User mengakses data admin.

Target:
- Setiap dokumen hanya dapat diakses pemiliknya.
- Semua operasi sensitif divalidasi server.
- Admin memiliki hak akses berbasis role.

Langkah Implementasi:

1. Audit seluruh collection.
2. Audit seluruh subcollection.
3. Identifikasi collection sensitif.
4. Terapkan ownership validation.
5. Terapkan role validation.
6. Pisahkan rule admin dan user.
7. Blok seluruh write operation yang tidak tervalidasi.
8. Audit seluruh query lintas user.
9. Buat testing rule otomatis.
10. Dokumentasikan seluruh akses collection.

9. SECRET MANAGEMENT

Audit:

- API key
- Exchange key
- Firebase config
- SMTP
- Resend

Target:

Tidak ada secret sensitif di frontend.

Catatan status implementasi:

- Kredensial exchange saat ini tidak disimpan di localStorage atau sessionStorage, tetapi masih dimasukkan melalui browser dan dikirim ke server dalam request.
- Kredensial tetap dapat diakses di browser selama sesi berjalan, sehingga target tidak ada secret sensitif di frontend belum sepenuhnya tercapai.
- Penyelesaian memerlukan vault kredensial di backend yang terikat pada autentikasi pengguna, validasi Firebase ID token di server, serta enkripsi dengan kunci yang dikelola server atau KMS.
- Sebelum vault tersedia, jangan menganggap kredensial exchange aman dari akses frontend atau menyatakan secret management production sudah tuntas.

Target:

Tambahkan:

Catatan status implementasi:

- Error middleware Express terdaftar setelah seluruh route API dan middleware Vite/production.

FASE 4 - DATABASE REVIEW
=====================================================================

Audit Collection:

users
transactions
positions
trade_history
network
member_directory

Audit:

- Query pattern
- Indexing
- Read frequency
- Write frequency
- Data duplication


Catatan status implementasi:

- Pola baca awal menggunakan listener seluruh positions, transactions, trade_history, price_alerts, dan getDocs seluruh network/positions. Listener transaksi dan trade sekarang dibatasi 50 dokumen terbaru; histori dapat dimuat per halaman dengan startAfter cursor.
- Network memakai cursor per 25 dokumen dan UID Firebase yang benar. Operasi maintenance positions membaca batch cursor 100 dokumen per request.
- firebase.json menghubungkan firestore.rules dan firestore.indexes.json. Manifest menyiapkan composite index untuk filter tipe/tanggal transaksi, simbol/side/timestamp trade, status/tanggal positions dan network, serta status/tanggal price alerts.
- Firestore tidak memerlukan composite index untuk query cursor sederhana yang hanya memakai satu orderBy; index komposit disediakan bagi pola filter server-side.
- Query transaksi berurut createdAt; dokumen transaksi legacy tanpa createdAt harus di-backfill sebelum perubahan dipasang pada database lama.
- Listener positions dan price_alerts tetap membaca seluruh dokumen agar bot dan price alert tidak kehilangan item; pindahkan UI ke halaman/virtualisasi sebelum memberi batas query.
- Rules wildcard dihapus. member_directory tidak dapat di-list dan hanya menerima data publik; email penuh, saldo, role, dan alamat deposit dibersihkan dari dokumen saat profil disinkronkan.
- wallet_ledger tidak dapat ditulis client. Penulisan lama dari client dihapus karena balanceBefore/balanceAfter dibuat tanpa saldo otoritatif; buat endpoint backend transaksi ledger sebelum mengaktifkan ledger finansial.
- Owner masih dapat mengubah field saldo pada dokumen users; mutasi saldo wajib dipindahkan ke backend tepercaya sebelum go-public.
- Firebase CLI/emulator tidak tersedia di workspace ini. JSON manifest lolos parse dan TypeScript/build lolos, tetapi rules belum diuji dengan emulator dan indexes belum dideploy.

Catatan status implementasi:

- Firestore rules tidak lagi memakai wildcard subcollection di bawah users; akses dibatasi ke positions, transactions, trade_history, network, price_alerts, dan wallet_ledger.
- member_directory hanya dapat dibaca per dokumen oleh user terautentikasi, tidak dapat di-list, dan hanya menerima field publik yang diizinkan. PII/saldo/alamat lama dihapus saat profil disinkronkan.
- wallet_ledger kini read-only dari client. Penulisan ledger harus dipindahkan ke backend tepercaya karena client tidak dapat dipercaya untuk menyatakan balanceBefore/balanceAfter.
- Listener transaksi dan trade mengambil 50 dokumen terbaru; tombol load-more memakai startAfter cursor. Referral network memakai cursor berdasarkan document ID. Pemindaian maintenance positions berjalan per 100 dokumen.
- firestore.indexes.json mencatat index komposit untuk transaksi, trade, posisi, network, dan price alert; firebase.json menghubungkan rules dan index manifest.
- Dokumen transaksi legacy tanpa createdAt perlu dimigrasikan sebelum query berurut createdAt dipakai pada project yang sudah berisi data lama.
- Listener positions dan price_alerts tetap memuat semua dokumen karena UI trading dan pemeriksaan alert bergantung pada seluruh koleksi; paginasi UI/virtualisasi diperlukan sebelum membatasi keduanya.
- Rules masih mengizinkan owner mengubah field saldo pada users/{userId}; mutasi saldo harus dipindahkan ke backend sebelum go-public.
- Firebase CLI/emulator tidak tersedia di workspace ini, sehingga rules/indexes belum diuji atau dideploy ke project Firebase.

FASE 5 - OBSERVABILITY
=====================================================================

Tambahkan:

Application Monitoring
Error Monitoring
Performance Monitoring
Audit Logging

Log yang wajib:

- Login
- Logout
- Deposit
- Withdraw
- Transfer
- Admin Action
- Permission Change
- Exchange Error

Catatan status implementasi:

- GET /api/health mengembalikan status, uptime, jumlah request, failure, slow request, dan rata-rata latency.
- Server mencatat request API lambat/gagal dengan requestId, route template, status, dan durasi; GET /api/health memberi uptime serta agregat request/failure/latency.
- Error API, retry exchange, dan aksi server-observed mengeluarkan structured logs. Aksi transfer, deposit, withdrawal, aktivasi, exchange order, dan bot lifecycle dicatat tanpa API secret, OTP, alamat, TXID, atau user PII.
- Client mengirim event login/logout, perubahan 2FA, aksi wallet/admin, render error, dan Web Vitals (CLS, FCP, INP, LCP, TTFB) melalui endpoint allowlist. Attribute disaring server-side; payload sensitif dan Web Vital ID tidak dicatat.
- Event dari browser ditandai untrusted_client_report; aksi server juga server_observed_unverified karena API belum memvalidasi Firebase ID token. Log ini berguna untuk observability tetapi belum merupakan audit finansial/administratif yang otoritatif.
- Firestore error logging tidak lagi mencatat email, provider info, atau user ID mentah.
- Log saat ini dikirim ke stdout/stderr. Retensi, alerting, dashboard, dan integrasi layanan eksternal (mis. Sentry/Cloud Logging) memerlukan konfigurasi deployment.

FASE 8 - SCALABILITY
=====================================================================

Target capaian: desain sistem yang tetap stabil saat jumlah pengguna naik, tanpa menurunkan CSAT atau mengorbankan keamanan dan akurasi ledger.

100 USER

Target:
- Semua fitur stabil.
- Tidak ada regressi pada login, wallet, trade history, referral, bot engine, atau observability.

Kebutuhan:
- Single Node / single instance aplikasi Express + Vite.
- Firestore read/write masih bersifat per-user.
- Endpoint health, rate limit, dan dashboard error sudah aktif.
- Monitoring dasar terhadap latency endpoint, 5xx rate, dan bot polling fallback.

Checklist:
- Validasi semua fitur pokok manual.
- Pastikan query riwayat menghindari `getDocs` full collection.
- Pastikan bot engine tetap mengurangi burst CPU dengan interval scheduler yang dapat dikontrol.

1000 USER

Target:
- Peningkatan load secara bertahap tanpa terjadinya spike error.
- Observability siap mendeteksi bottleneck di API / Firestore / bot engine.

Tambahkan:
- Monitoring lebih baik: request latency, Firestore read count, 5xx rate, bot engine queue depth.
- Redis cache untuk ticker data cepat, market snapshot, dan rate-limit counter.
- Per-user session cache ring buffer di aplikasi backend.
- Debounce / coalesce query market dan trade summary.
- Batasi polling bot per-user: scheduler bukan lagi client polling penuh.

Checklist:
- Log request API dipisahkan by route dan status.
- Firestore read/write per query dibatasi maksimal 1 batch per request.
- Bot engine tidak lagi mengandalkan in-memory polling yang terlalu banyak untuk semua user.

10000 USER

Target:
- Aplikasi dapat menangani traffic concurrent yang lebih tinggi.
- Tidak ada bottleneck pada single process backend.

Tambahkan:
- Redis untuk cache hot data, session, dan rate limiting.
- Cache Strategy:
  - TTL 15-30 detik untuk market snapshot.
  - TTL 60 detik untuk portfolio summary.
  - TTL 5-10 menit untuk data referral tree yang jarang berubah.
- Background Worker untuk bot engine, exchange sync, dan rebalancing.
- Queue System: job berdasar order/market per user.
- Firestore query optimization: pagination, index exact match, batch write terbatas.
- Worker memindahkan operasi yang tidak perlu dari request thread.

Checklist:
- Bot engine dipisah dari web API process.
- Exchange jobs masuk queue dengan retry backoff.
- Protected API tidak lagi membaca data terlalu banyak dari UI layer.

50000 USER

Target:
- Aplikasi mulai tampak sebagai sistem multi-service.
- Semua fungsi penting sudah terbagi antara API, worker, scheduler, dan storage.

Tambahkan:
- Background Worker per-user bot execution.
- Queue System: BullMQ / Redis queue, DLQ, retry policy, dead-letter logs.
- Event-driven architecture untuk order created / wallet updated / trade settled.
- Scheduler job yang ditulis ke durable queue, bukan langsung diproses inline.
- Separasi Bounded Context:
  - Auth & Session
  - Wallet & Ledger
  - Bot Execution
  - Market Data
  - Notification & Audit
- Log aggregation ke centralized system: Cloud Logging / Sentry / Datadog.

Checklist:
- Semua mutasi finansial melalui backend trusted service.
- Ledger transaksi masuk ke sistem append-only yang terpisah dari read-model UI.
- Pekerjaan bot tidak lagi memblokir endpoint API utama.

100000 USER

Target:
- Sistem siap untuk traffic skala besar dan kompleksitas operasional tinggi.

Evaluasi:
- PostgreSQL sebagai sumber truth ledger dan transaksi finansial.
- Firestore hanya untuk realtime user session / ringan sync / cache tertentu.
- Event Driven Architecture: producer-consumer pattern antar service.
- Dedicated Backend Services:
  - Auth service
  - Wallet/ledger service
  - Bot execution service
  - Notification service
  - Market data service
  - Admin audit service
- Redis cluster untuk cache dan queue.
- Database sharding / partitioning untuk kebutuhan merchant / portfolio / user event.
- Background workers dipisah ke worker pool dengan autoscaling.
- Observability yang lengkap: SLI/SLO, distributed tracing, error budget, alerting.

Checklist:
- Ledger harus dipindah ke backend authoritative system.
- Firestore bukan lagi source of truth utama untuk transaksi keuangan.
- Perubahan status bot, order, settlement, dan withdrawal dikelola lewat event stream.
- Setiap operasi kritis memiliki idempotency key dan audit trail.

Kesimpulan:
- Saat ini project cocok untuk scale 100-1000 user dengan penguatan observability dan queueing dasar.
- Untuk 10.000+ user diperlukan Redis + worker queue + backend separation.
- Untuk 50.000-100.000 user, dibutuhkan PostgreSQL + event-driven architecture + dedicated services, bukan hanya Firestore untuk semua domain.

DEFINISI GO PUBLIC
=====================================================================

Produk hanya dianggap siap go public apabila:

1. Tidak ada mock data masuk production.
2. Firestore rules telah diaudit.
3. Role management telah benar.
4. Wallet menggunakan ledger.
5. LocalStorage bukan source utama.
6. Audit log aktif.
7. Monitoring aktif.
8. Error tracking aktif.
9. Setup developer terdokumentasi.
10. Recovery process terdokumentasi.
11. Backup strategy terdokumentasi.
12. Authentication telah di-hardening.
13. Exchange integration memiliki fallback.
14. Semua transaksi tervalidasi server.
15. Security review selesai.

Catatan implementasi prioritas P0:

- semua mutasi finansial harus melalui backend authoritative validation; route /api/wallet/authorize-financial-action merekam validasi server-side terhadap amount, userId, dan action.
- wallet_ledger tetap non-writable dari client. Client hanya boleh membaca atau menampilkan saldo; mutasi sebenarnya harus melalui backend trusted service.
- saldo final dan ledger tidak boleh diubah hanya dari localStorage atau UI patching.
